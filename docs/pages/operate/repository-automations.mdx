# Repository Automations

Repository Automations let an operator configure repeatable GitHub and Linear
work without putting an LLM in the webhook router. The Console evaluates a
small declarative policy, records the event, and only then authorizes an
existing durable agent session to continue work.

Open **Automations** in Centaur Console as an administrator. Policies start in
**Observe** mode. Review the recorded workstreams first, then deliberately
switch a policy to **Act automatically**. Act mode requires an explicit,
operator-marked **execution role**. Choose a dedicated role containing only the model,
repository credential, and tools that this policy needs; no webhook text can
select or alter that role.

## What is durable

For one GitHub pull request, every policy-selected event uses the same
`github-manage:<owner>/<repo>:<number>` session. For one Linear issue, every
policy-selected event uses `linear:<issue-id>`. A webhook therefore adds
context to the established workspace instead of creating another unrelated
sandbox.

```text
verified GitHub / Linear webhook
             |
             v
normalized event -> Console policy + audit record
             |                 |
             |                 +-> ignored / observed / acted
             v
existing PR or issue session -> api-rs execution -> platform reply / PR work
```

The Console records a workstream for each PR or issue, including the stable
session key and recent event count. When api-rs creates the matching derived
principal, Console attaches the policy's selected execution role only while
the latest event remains authorized. Disabling the policy, changing it out of
Act mode, or receiving a newly ineligible event revokes that policy-owned role
binding. It keeps only compact event metadata; raw webhook bodies and
credentials do not enter the policy store.

## Optional Slack activity report

Each policy can optionally name a Slack channel and enable **Report accepted
work** and/or **Report pull requests created by the app**. Accepted-work
reporting posts one compact notification when an Act policy first accepts a new
PR or issue workstream (or accepts it again after a safety block). PR-created
reporting posts only for a signed `pull_request.opened` webhook whose PR author
matches the configured GitHub App login. It does not infer that a human-created
PR came from an agent, and it does not turn the report into another agent run.

Each notice links only the provider source item and the Console audit record;
accepted-work notices also list the deterministic authorized action. Neither
kind repeats raw webhook content, agent output, credentials, or a message for
every continuation/replayed delivery. Direct messages are deliberately not
inferred from an issue assignee: a future identity-mapping policy can add that
explicitly without making a Slack routing guess.

The channel must already be accessible to the installed Slack bot. Leaving the
setting off keeps the audit Console-only. Slack delivery itself runs as a
native, checkpointed workflow keyed by the persisted automation event, so a
retried Console job cannot create a second root message.

## GitHub policies

A GitHub policy scopes to one `owner/repository`. It can independently enable:

- automatic review of eligible non-draft pull requests;
- response to submitted review feedback;
- failing-check repair after all checks for a commit settle;
- merge-conflict resolution; and
- an explicitly enabled, verified manual mention. A manual mention can start a
  scoped turn on a draft PR, but it still must meet the configured repository,
  base-branch, required-label, and excluded-label gates; and
- deterministic auto-merge, explicitly opt-in and still constrained by branch
  protection, draft state, and the hold label.

Automatic review is organized into review epochs. By default, each epoch gets
one broad/new-risk review and two repair-validation rounds
(`githubbot.reviewMaxRoundsPerEpoch: 3`). Validation rounds inspect only
accepted fixes, newly changed risk surfaces, and regressions. Hidden finding
fingerprints in GitHub comments preserve accepted/rejected/fixed decisions
across line movement.

A new production file, dependency manifest, auth/data/API/infra boundary, or
`githubbot.reviewEpochMinChangedLines` non-generated changed lines (default 50)
starts an epoch. Test/docs/generated-only changes do not. A material
bot-authored expansion pauses for human approval; it cannot reset its own
budget. After `githubbot.reviewMaxEpochs` automatic epochs (default 3), split the
PR or explicitly request Githubbot as reviewer to continue. A changed
authorization/security surface may still trigger a narrowly scoped P0/security
inspection after the normal cap. Human-submitted reviews are not budgeted, but
responses to bot-authored feedback are. The bundled reviewer requires
exact-line evidence, a reachable failure path, material impact, and high
confidence before it posts a finding.

Epoch classification is deterministic; no model decides whether it earned more
review budget. Githubbot compares the last reviewed head with the new head and
the cumulative production-only PR diff. Pure rebases, detected whitespace-only
changes, and test/docs/generated-only deltas stay in the current epoch. PRs over
the bounded 250-production-file inventory pause for an explicit human review
request instead of silently classifying a partial file set. All bot-authored
reviewers have independent response budgets, plus one aggregate PR/epoch cap so
one bot cannot starve every other bot and adding bots cannot create an unbounded
loop. The audit trace
records changed-line counts and the exact classifier reasons for every review.

### Cross-model review groups

The default strategy is one reviewer. A reviewed, source-managed GitHub policy
may opt into `review_orchestration.mode: "cross_model"` with two or three
independent Centaur model profiles and one synthesizer. Each reviewer gets its
own isolated PR session, model budget, and Console execution record; reviewers
return structured reports privately. The synthesizer re-checks the live head
and the relevant claims, then is the only profile allowed to publish the one
consolidated GitHub review.

The configuration is deliberately bounded: at most three reviewers, at most two
fallback attempts per profile, three runs per profile per epoch, and a maximum
of three concurrent reviewers. A fallback is used only after a provider outage
or a confirmed unsupported model capability. Credential errors, cancellations,
and ambiguous failures pause rather than silently changing models. Console
records the requested and resolved model, reviewer ID, epoch, round, and any
fallback category; GitHub receives neither model transcripts nor provider error
details.

External reviewers such as Cursor or Greptile are not Centaur profiles. Their
existing GitHub reviews still feed the normal per-reviewer repair budgets, so
adding them does not multiply automatic repair loops.

Use allowed base-branch patterns such as `main` or `release/*`, required labels,
and excluded labels to define eligibility. Existing assigned-review and
bot-owned PR behavior remains available; the policy only extends automation to
other eligible PRs.

Enable the GitHubbot, expose `POST /api/webhooks/github`, and subscribe the
GitHub App or webhook to **Issue comments**, **Issues**, **Pull requests**,
**Pull request reviews**, **Pull request review comments**, **Check runs**,
**Check suites**, **Statuses**, and **Workflow runs**. Comment-driven work
retains its separate fail-closed GitHub author-association gate.

## Linear policies

A Linear policy scopes to a team, optionally narrowed to one project. It can
pick up new or updated issues only when configured readiness checks pass:

- title, description, and optional acceptance-criteria requirements;
- configured ready workflow states; and
- excluded labels such as `no-agent`.

Map a simple policy to one GitHub repository and optional reviewers. For a
team-wide policy, use explicit repository routes instead of asking the agent to
infer a target. A route can select a Linear project ID, required issue labels,
or both; if both are present, either selector can choose that same reviewed
repository. Each ready issue must match exactly one route; zero or multiple
matching routes are recorded as an ignored decision and cannot start a sandbox.
A route may override reviewers, opt into the fixed QA executor for that
repository, and declare an opt-in preview label:

```json
{
  "linear": {
    "issue": "ready_issues",
    "repository_routes": [
      {
        "repository": "acme/widgets",
        "linear_project_ids": ["00000000-0000-0000-0000-000000000000"],
        "qa_enabled": true
      },
      {
        "repository": "acme/web",
        "required_labels": ["repo:web"],
        "reviewer_team_slugs": ["frontend"],
        "preview_label": "preview"
      }
    ]
  }
}
```

`github_repository` and `repository_routes` are mutually exclusive, so adding
routes cannot silently turn a formerly single-repository policy into a broad
fallback. A `preview_label` is applied only after the agent opens a draft PR for
a user-visible change. It must be an already-reviewed repository label whose
workflow creates a real preview; the agent reports a URL only after verifying
it from the PR's checks or comments.

When a routed policy also enables deterministic QA orchestration,
`qa_enabled: true` is required on the selected route. This keeps a QA status
transition for another repository from accidentally dispatching a fixed QA
workflow. Legacy single-repository QA policies remain compatible.

In Console, native (non-source-managed) Linear policies expose the same
project-ID and label route fields. Source-managed policies stay read-only in
Console and must be changed in their reviewed configuration before deployment.

The agent re-checks readiness before coding, opens a linked PR without merging
it, requests the configured human reviewers, and attaches a real verified
screenshot for a user-visible change when available. It must not fabricate a
screenshot. Once a PR exists, it can mark the Linear issue `In Review`.

## Enable the policy plane

The Helm chart keeps the policy plane off by default. Enable it only after the
shared secret source contains a generated
`CENTAUR_AUTOMATION_INGRESS_TOKEN` value:

```yaml
automation:
  enabled: true
```

When enabled, the chart gives the token only to Console, Githubbot, and
Linearbot. The bots use it solely to send already-verified, normalized event
summaries to Console's internal automation endpoint. It is not an operator API
key and cannot grant sandbox permissions.

Policies do not create credentials or widen a role. Configure and review a
dedicated execution role before moving a policy from Observe to Act. The
policy then applies that pre-existing role only to its matching durable
workstream principal; it does not grant the role to the trigger service or to
other PRs/issues.

## Safe rollout

1. Deploy with `automation.enabled=true`.
2. Create one narrow policy in **Observe** mode.
3. Exercise a real webhook and inspect its workstream and associated session.
4. Create or review a dedicated execution role, mark it for repository automation, and give it only the repository and tool access it needs.
5. Select that role and change the policy to **Act automatically**.
6. Enable auto-merge only after the observed behavior and repository protection
   rules are satisfactory.

An unavailable Console, missing ingress token, invalid webhook signature, or
nonmatching policy fails closed: no new policy-driven agent turn starts.
